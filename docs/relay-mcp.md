# Relay MCP (WDY-3656, contract WDY-3657)

Web chats (ChatGPT, Claude) reach Wendy through the user's own CLI session.
The hosted relay holds no Wendy credential and is never a principal: every
tool call is executed by the user's CLI (`wendy cloud mcp`) and reaches cloud
as an ordinary operator-signed `SignedRequest`. Two-key authority is unchanged.
Wire: `wendycloud/v2/relay_mcp.proto` (`RelayMcpService`) and the channel
fields on `wendycloud/v2/signed_request.proto`.

## Three hops

1. **Web chat → relay.** Streamable-HTTP MCP with a wendy-auth bearer
   (OAuth below). The relay validates it locally against wendy-auth's JWKS and
   never forwards it.
2. **Relay ↔ CLI.** The CLI calls `OpenRelaySession` (signed, realm settings
   checked) and holds the session with one `RelaySession` stream, outbound
   from the user's machine. The relay forwards MCP JSON-RPC as `McpFrame`s;
   `sequence` starts at 1 per sender and a gap or repeat ends the stream.
3. **CLI → cloud.** The CLI runs the same tool set as local `wendy mcp serve`
   and signs every cloud call with the operator key, setting
   `channel = REQUEST_CHANNEL_HOSTED_MCP`, `mcp_client_id` and
   `relay_session_id`.

## Binding gate

A web bearer alone binds nothing. The relay asks a CLI session to approve
only a bearer whose `sub` and normalized `tenant_uuid` match that session's
user and tenant. An unpaired `tools/call` returns the pairing code and asks
the CLI to show the same code with the client name and ID. The user compares
the two codes and accepts the `PairingRequested` prompt in the CLI or app.
The chat does not collect a code. The CLI drops frames for any binding it
did not accept.

Approval belongs to one signed-in OAuth connection, identified by `sub`,
normalized `tenant_uuid`, `client_id`, and the signed `relay_grant_id` claim.
It applies across chats using that same connection while the approved CLI
session remains open. A separate authorization, another client, another
subject, or another tenant needs its own approval. Reinitializing the same
connection reuses its pending prompt or accepted approval. The relay still
validates the bearer on every HTTP request and checks revocation before
reusing approval.

Every HTTP `initialize` creates a fresh `Mcp-Session-Id`, even when it shares
approval with another transport. The relay sends all of those transports
through the original binding ID accepted by the CLI. Each forwarded request
gets a unique relay request ID, and its response restores the original ID
and its JSON type. Cancellation targets only the matching request on the
same HTTP transport. Two chats can both use request ID `1` without sharing
responses or cancelling each other's calls. These mappings stay inside the
relay; the existing CLI frame and pairing messages do not change.

During expansion, a missing or non-string `relay_grant_id` uses the SHA-256
digest of the exact verified access token in place of a grant ID. The raw
bearer is not stored or forwarded. This fallback never treats the same
subject and client as sufficient to inherit approval. An empty string claim
is refused. A malformed optional claim does not reject otherwise valid
tokens on Cloud's other authentication paths.

## Tool manifest

`docs/relay-mcp-tools.json` is the tool set the CLI serves to a hosted chat,
generated by `wendy mcp manifest` (each tool's name, title, description,
input schema and annotations: `readOnlyHint`, `destructiveHint`,
`idempotentHint`, `openWorldHint`). It is exactly what the relay channel
serves, paired or not: the CLI leaves out tools that take a credential from
the chat (`wifi_connect`, `provisioning_start`; both stores ban collecting
one), the hidden `container_attach`, `wendy_tools` group switching and
device-app tools, and refuses calls to them. Local `wendy mcp serve` keeps
every tool. The relay serves it **unpaired**: it answers `initialize`
and `tools/list` from it for any authorized chat, and answers `tools/call`
before pairing with the pairing instruction. App directories read the same
list. Its `version` is `<CLI version>+<tool set hash>`; the relay reports it
as `OpenRelaySessionResponse.manifest_version`, and the CLI refuses to pair
(with a warning) when the hash differs from its own tool set. A CLI release
that changes a tool regenerates this file.

## Lifetime

The session lives with the CLI's stream: CLI exit, network loss or an
explicit close ends it and every binding; a reconnecting CLI opens a new
session and the chat pairs again. An unattached session ends 60 s after
open; an attached one after 8 h without a forwarded frame. The relay sends
the HTTP/2 keepalive pings, so the path to it must be a passthrough load
balancer or another front that does not cap stream duration (an L7 proxy or
Cloud Run cuts streams at 60 min).
The web bearer lives 1 h; each refresh re-checks the realm setting and the
user's account in wendy-auth (WDY-3364). Grant-backed approval survives a
refresh carrying the same `relay_grant_id`, subject, tenant and client, but
every request still needs a currently valid bearer.

Legacy exact-token approval expires at the verified access token's expiry.
The registry removes it and closes any CLI session attached to it. The user
must run `wendy cloud mcp` again and approve the refreshed legacy token.
Closing the session avoids leaving an expired binding occupying the CLI,
which accepts only one binding during a command invocation. It does not
silently transfer approval to the refreshed token.

## Realm settings and claims

| Setting | Claim on the operator access token | Default | Enforced by |
|---|---|---|---|
| Allow MCP | `allow_mcp` (bool) | on | CLI refuses to start MCP; cloud refuses `MCP_LOCAL` and `HOSTED_MCP` requests |
| Allow Hosted MCP (requires Allow MCP) | `allow_hosted_mcp` (bool) | off | wendy-auth refuses the relay authorization and refresh; relay refuses `OpenRelaySession`; cloud refuses `HOSTED_MCP` requests |

An absent claim reads as false. Ceiling: the channel marker is set by the
user's client and is not signed. A modified CLI, and every CLI released
before this contract, omits it, so Allow MCP binds only current honest
clients. Allow Hosted MCP also holds at wendy-auth and the relay, which no
client controls.

## Against a compromised relay

The chat holds no key, so a relay can forge a call that looks real. A
compromised relay silently reads whatever the user can read through any
bound session's allow-listed tools; nothing on the wire prevents that. The
mitigations make a forged state change worthless and every forged call
visible:

- **Per-call confirmation** in the CLI/app, showing tool and arguments, for
  every state-changing tool: at least the AAA §5.1 step-up set (deploy,
  container control, config push, tunnel open, unenroll). Reads flow freely.
- **Per-binding tool allow-list**, chosen at pairing (preset: read-only),
  enforced by the CLI. The relay cannot widen it and never sees it.
- **Live call stream** in the app with the client name; one click ends the
  session.
- **Audit** in cloud: `channel`, `mcp_client_id`, `relay_session_id` and the
  signed `correlation_id` on every call.

## OAuth (wendy-auth is the authorization server)

One relay resource URL per environment (the connector URL, e.g.
`https://mcp.<env>.wendy.dev`), the same for every organization:

- Its protected-resource metadata names a dedicated wendy-auth relay issuer
  (`https://auth.<env>/relay`, final path set by wendy-auth) as the single
  authorization server. Its authorize endpoint is the universal sign-in page,
  which resolves the user's realm. A tokenless call gets 401 pointing at the
  metadata.
- Authorization code + PKCE, scope `mcp:relay`, `resource=<resource URL>` on
  both the authorization and token requests.
- Token: `iss` = the relay issuer, `aud` = the resource URL, claims `sub`,
  `realm` (slug), `tenant_uuid`, `allow_hosted_mcp`. The relay takes the
  tenant from `tenant_uuid`. Such a token is refused by cloud's own services
  (wrong `iss`/`aud`; `RelayMcpService` refuses scope `mcp:relay`).
- Optional `relay_grant_id`: a non-empty JSON string signed into the relay
  access token by wendy-auth. Its value comes only from the server-owned
  refresh-token family. Refreshes in that family keep the value; a separate
  authorization gets a different value. Client metadata, request parameters
  and headers cannot choose or override it. Cloud treats the value as opaque.
- Client identity: client ID metadata documents (the `client_id` is an HTTPS
  URL wendy-auth fetches); dynamic client registration only as fallback.
  Token-endpoint auth `none` or `private_key_jwt`.
- The bearer is not sender-constrained (the chats cannot do DPoP), which is
  why it grants nothing without the binding gate.

The console shows nothing per organization beyond the pairing UX
(cloud, WDY-3659).

## Phases

expand (this): proto and docs. migrate: wendy-auth settings, claims and AS
features (no proto dependency); then cloud (relay, channel refusal and audit)
and the CLI against this contract; cloud enforces the claims only once
wendy-auth emitting them is live in that environment. contract: none needed.

WDY-3758 expands the OAuth contract with optional `relay_grant_id` and
separates HTTP transport IDs from pairing approval. Cloud #830 accepts both
legacy exact-token identity and grant identity. This phase has no new
wendy-auth, pki-core or CLI minimum beyond the existing hosted MCP support.
The unchanged CLI binding and frame messages work with both token forms.

Migrate is wendy-auth #345 emitting the claim. It follows a Cloud #830
release tagged and confirmed live on prod, and its release notes name that
Cloud version. Approval across token refresh needs both changes; before
the issuer emits the claim, token refresh still requires a new CLI session
and pairing. This change removes no old token shape. Requiring the claim or
removing exact-token fallback is a separate contract phase, at least one
release after migrate and only after the required peers are live on prod.
